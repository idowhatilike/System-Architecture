# 📘 MODULE WORKBOOK 01: RANH GIỚI USER/KERNEL SPACE & SYSTEM CALLS

**Level** : Systems Core | **Time Target** : 2 - 3 Hours | **Prerequisites** : C Basic, Linux Terminal

### 1. Định Hướng Nghiên Cứu Core (First-Principles Research Directives)

* **Tài liệu nguồn bắt buộc tự đọc**:
  - *OSTEP*: Chapter 4 (Abstraction: The Process), Chapter 6 (Mechanism: Limited Direct Execution).
  - *Linux Man Pages*: `man 2 syscalls`, `man 1 strace`.

* **Câu hỏi định hướng nghiên cứu sâu**:
  1. **Mode Switch vs Context Switch**: Phân tích chi tiết sự khác biệt giữa chuyển mức đặc quyền (Privilege Level Switch: Ring 3 → Ring 0) và chuyển tiến trình (Process Context Switch). Khi chuyển mức đặc quyền, CPU thay đổi những tài nguyên phần cứng nào (thanh ghi `CS`, Stack Pointer `RSP`), và khi Context Switch xảy ra, những tài nguyên nào bị thay đổi (`CR3`, TLB cache, CPU Registers)?
  2. **Cơ chế vDSO & vvar**: Tìm hiểu lý do tại sao hàm `clock_gettime()` hoặc `gettimeofday()` trên Linux hiện đại lại không tốn chi phí cho một System Call truyền thống. Kernel ánh xạ hai trang bộ nhớ read-only `[vvar]` và `[vdso]` vào User Space của tiến trình như thế nào?
  3. **User-space Buffering**: Phân tích cơ chế bộ đệm tạm mặc định (thường là 8KB) của thư viện `glibc` (`stdio.h`). Tại sao việc gom các thao tác I/O nhỏ thành một lệnh System Call duy nhất lại làm giảm áp lực cho Kernel?

* **Bài toán đánh đổi & Định lượng**:
  - Hãy tính toán tổng chi phí thời gian hao phí (overhead) khi thực hiện 1.000.000 lệnh System Call `write()` trực tiếp so với 122 lệnh `write()` được gom qua bộ đệm `fwrite()` 8KB. Giả định mỗi lần chuyển ngữ cảnh từ Ring 3 → Ring 0 tiêu tốn khoảng 100 – 300 chu kỳ CPU (CPU cycles).

### 2. Yêu Cầu Thiết Kế Sơ Đồ Kiến Trúc (Architectural Mapping Spec)

* **Yêu cầu tự vẽ sơ đồ**: 
  Thực hiện vẽ sơ đồ luồng thực thi và trạng thái bộ nhớ (bằng sơ đồ khối ASCII hoặc Mermaid) mô tả hành vi của tiến trình khi ghi dữ liệu I/O qua `fwrite()` (Phiên bản A) so với System Call `write()` trực tiếp (Phiên bản B).

* **Các cấu trúc Kernel & Memory bắt buộc phải xuất hiện trong sơ đồ**:
  - Không gian **User Space (Ring 3)**: User Stack, `glibc I/O Buffer` (8KB), User Code Segment, các trang bộ nhớ `[vdso]` và `[vvar]`.
  - Ranh giới **User/Kernel Boundary**: Lệnh assembly `syscall` / Bảng ngắt `Interrupt Descriptor Table (IDT)`.
  - Không gian **Kernel Space (Ring 0)**: Kernel Stack, `task_struct`, Bảng quản lý file descriptor (`struct file* fd_array[]`), `struct file`, `struct inode`, Kernel Page Cache.

### 3. Đề Bài Code Lab & Thử Thách Break-Check (Lab Specifications)

* **Đặc tả Đồ án (`lab1_syscall.c`)**:
  Tự viết một chương trình C (chuẩn C11) từ con số 0 thực hiện bài toán ghi 1.000.000 ký tự ra đĩa theo 2 chế độ (chọn qua tham số dòng lệnh):
  - **Chế độ A (`fwrite_mode`)**: Sử dụng hàm `fwrite()` từ thư viện `stdio.h` để ghi từng ký tự/chuỗi nhỏ trong vòng lặp 1.000.000 lần.
  - **Chế độ B (`direct_write_mode`)**: Sử dụng trực tiếp System Call `write(2)` (thông qua `<unistd.h>`) để ghi từng ký tự trong vòng lặp 1.000.000 lần.

* **Toolchain Requirement**:
  Biên dịch chương trình bằng `gcc` với các cờ kiểm tra nghiêm ngặt, vô hiệu hóa tối ưu hóa để quan sát đúng hành vi gốc:
  ```bash
  gcc -Wall -Wextra -Wpedantic -Werror -O0 -g -std=c11 lab1_syscall.c -o lab1_syscall
  ```

* **Thử thách Break-Check**:
  - **Cấu hình lại bộ đệm**: Thay đổi chế độ bộ đệm của `fwrite()` bằng hàm `setvbuf()` chuyển sang `_IONBF` (Unbuffered - không bộ đệm). Quan sát sự thay đổi về số lượng System Call phát sinh và đo đạc sự sụt giảm hiệu năng.
  - **Bẫy con trỏ bất hợp lệ**: Cố tình truyền một bộ đệm chứa con trỏ `NULL` hoặc địa chỉ không hợp lệ vào System Call `write()` trực tiếp. Quan sát mã lỗi trả về (`EFAULT`) và giá trị `errno` mà Kernel phản hồi mà không làm sụp đổ Kernel.

### 4. Nhiệm Vụ Observability & Debugging (Investigation Tasks)

* **Các công cụ CLI bắt buộc sử dụng**: `strace`, `time`, `/proc/[PID]/maps`.

* **Lập luận & Phân tích Output**:
  1. Thống kê tổng số lượng System Call phát sinh:
     ```bash
     strace -c ./lab1_syscall fwrite
     strace -c ./lab1_syscall direct_write
     ```
     *Phân tích*: So sánh cột `% time`, `seconds`, `usecs/call`, và số lượng `calls` của System Call `write`.
  2. Bắt dấu kích thước buffer của từng lệnh System Call:
     ```bash
     strace -e trace=write ./lab1_syscall fwrite
     ```
     *Phân tích*: Kiểm tra tham số dung lượng truyền vào mỗi lần gọi `write()` trong log của `strace` (ví dụ: `write(1, "...", 8192)`).
  3. Kiểm tra bản đồ bộ nhớ tiến trình để xác minh vDSO:
     ```bash
     cat /proc/self/maps | grep -E "vdso|vvar"
     ```
     *Phân tích*: Giải thích ý nghĩa quyền truy cập (`r-xp` cho `vdso`, `r--p` cho `vvar`) và địa chỉ ánh xạ của hai vùng nhớ này trong User Space.

### 5. Phân Tích Cạm Bẫy & Kịch Bản Sự Cố (Hazard Case Studies)

* **Sự cố 1: Syscall Thrashing trong dịch vụ Logging tải cao**:
  - *Tình huống*: Một dịch vụ backend thực hiện ghi log bằng cách gọi `write(fd, log_line, len)` trực tiếp cho mỗi request. Khi hệ thống đạt 50,000 req/s, CPU bị nghẽn ở mức 100% trong đó thời gian thực thi Kernel (`%sys`) chiếm hơn 70%.
  - *Câu hỏi nghiên cứu*: Cơ chế Kernel xử lý như thế nào khi bị oanh tạc bởi hàng chục ngàn System Call nhỏ liên tục? Thiết kế mô hình User-space Ring Buffer / Double Buffering như thế nào để khắc phục hiện tượng này?

* **Sự cố 2: Tín hiệu can thiệp (EINTR) và Partial Write**:
  - *Tình huống*: Khi ứng dụng phát lệnh `write()` trực tiếp với dung lượng lớn, tín hiệu từ OS (Signal) ngắt ngang khiến System Call trả về số byte ghi được ít hơn mong đợi (Partial Write) hoặc trả về `-1` với `errno = EINTR`.
  - *Câu hỏi nghiên cứu*: Tại sao chương trình không được giả định `write()` sẽ luôn ghi đủ số byte yêu cầu trong 1 lần duy nhất? Hãy mô tả cấu trúc vòng lặp ghi an toàn (`robust write loop`) để chống mất mát dữ liệu.

### 6. Khung Nghiệm Thu Exit Gate (Self-Assessment Framework)

* **Knowledge Check**:
  1. Phân biệt chính xác sự khác nhau giữa Mode Switch (Ring 3 → Ring 0) và Context Switch về mặt tài nguyên phần cứng bị tráo đổi.
  2. Giải thích cơ chế vDSO giúp hàm `clock_gettime()` đạt tốc độ tương đương một hàm C thông thường mà không qua ngắt Kernel.
  3. Giải thích tại sao với tệp 1.000.000 ký tự, `fwrite()` chuẩn chỉ phát ra xấp xỉ ≈ 122 System Calls, trong khi lệnh `write()` trực tiếp trong vòng lặp phát ra đúng 1.000.000 System Calls.

* **Break Check Target**:
  Tái hiện thành công sự sụp đổ hiệu năng bằng cách ép `fwrite()` chạy ở chế độ `_IONBF` (Unbuffered) và xác nhận số System Call nhảy vọt lên đúng 1.000.000 cuộc gọi thông qua `strace -c`.

* **Verification Metric**:
  - Báo cáo kết quả thời gian `sys` (Kernel time) từ lệnh `time`: Chế độ ghi trực tiếp chậm hơn chế độ dùng bộ đệm ít nhất 10 – 50 lần.
  - Báo cáo `strace -c` xác minh số lượng cuộc gọi `write`:
    - Phiên bản A (fwrite): $\approx \lceil 1.000.000 / 8192 \rceil \approx 123 \text{ calls}$
    - Phiên bản B (direct write): $1.000.000 \text{ calls}$
